1. สรุปใน 30 วินาที

ระบบจัดการแบบสำรวจ (Survey Engine) ออกแบบมาได้ดีมาก วิธีการแยกคำถาม เส้นทาง และตรรกะการแตกกิ่งออกเป็นฟังก์ชันเล็กๆ ที่เป็น "Pure functions" (ฟังก์ชันที่คำนวณค่าเท่านั้น โดยไม่ยุ่งกับฐานข้อมูลหรืออินเทอร์เน็ต) ถือเป็นการออกแบบที่ยอดเยี่ยม ทำให้ทดสอบและเข้าใจได้ง่าย แถมยังมีชุดการทดสอบ (Test suite) ครอบคลุมไว้ด้วย เก่งมากครับ

จุดอ่อนจะอยู่บริเวณ "ขอบ" ของระบบ โดยเฉพาะเรื่อง ประตูความปลอดภัย ของหน้าแอดมิน และสิ่งที่เกิดขึ้นเมื่อเกิด ข้อผิดพลาด (Error handling) ซึ่งเป็นส่วนที่นักศึกษามือใหม่มักจะยังไม่เคยเรียน ดังนั้นไม่ต้องกังวลไปครับ ทั้งหมดนี้แก้ไขได้ไม่ยาก

ส่วนงานผลการตัดสินปัญหาที่แย่ที่สุด
Survey engine (เส้นทาง/สถานะ)🟢 แข็งแรงระบบค้างหากมีการเปลี่ยนไฟล์แบบสำรวจขณะที่ผู้ใช้กำลังทำอยู่
การเข้าสู่ระบบ Dashboard / ยืนยันตัวตน🔴 อ่อนแอมีการใส่รหัสผ่านเริ่มต้นไว้ในซอร์สโค้ดตรงๆ
การจัดการข้อผิดพลาด (Error handling)🔴 อ่อนแอรายละเอียดการค้างทั้งหมดถูกส่งคืนไปยังใครก็ตามที่ส่งคำขอมา
Database layer🟡 พอใช้การตรวจสอบการเข้ารหัสถูกปิดไว้
การทดสอบ (Tests)🟢 มีอยู่ยังไม่ครอบคลุมเส้นทางความปลอดภัย (Security paths)

2. ความหมายของแถบสี

Criticalความเสี่ยงด้านความปลอดภัยหรือข้อมูลสูญหายจริง ต้องแก้ก่อนให้คนจริงๆ ใช้แอปฯ
Importantบั๊กหรือจุดอ่อนที่จะสร้างปัญหาในภายหลัง ควรแก้เร็วๆ นี้ แต่ยังไม่ทำให้ระบบพังในวันนี้
Minorเรื่องสไตล์ / ความเรียบร้อย แก้ก็ดีแต่ไม่เร่งด่วน ("nit" = เรื่องจุกจิก)

3. 🔴 ระดับวิกฤต — ต้องแก้ก่อนเปิดให้คนใช้จริง

Critical

C1 · มีการใส่รหัสลับ (Secret password) ไว้ในซอร์สโค้ดโดยตรง app/utils/auth.py:9

หน้า Dashboard ของคุณใช้สิ่งที่เรียกว่า JWT (เหมือน "สายรัดข้อมือดิจิทัล" ที่เซิร์ฟเวอร์มอบให้เพื่อพิสูจน์ว่าคนนั้นล็อกอินแล้ว) เพื่อให้สายรัดข้อมือนี้ไม่สามารถปลอมแปลงได้ เซิร์ฟเวอร์จึงต้องเซ็นชื่อด้วยรหัสลับ (Secret key) และนี่คือวิธีที่รหัสลับนั้นถูกโหลดเข้ามา:

SECRET_KEY = os.getenv("SECRET_KEY", "your-super-secret-key-change-me")

ค่าที่สอง "your-super-secret-key-change-me" คือ ค่าสำรอง (fallback): "ถ้าไม่มีใครตั้งรหัสลับจริง ให้ใช้ตัวนี้" ปัญหาก็คือข้อความนี้ตอนนี้กลายเป็นของสาธารณะแล้ว เพราะมันอยู่ในโค้ดของคุณบน GitHub และ เขียนไว้ใน CLAUDE.md ของคุณด้วย

การเปรียบเทียบ: เหมือนโรงเรียนที่ซื้อกุญแจราคาแพงมาติดห้องเซิร์ฟเวอร์ แต่กุญแจทุกลูกถูกตั้งรหัสมาจากโรงงานเป็น 0-0-0 และรหัสนี้ถูกพิมพ์ไว้ในคู่มือด้วย ถ้าครูลืมเปลี่ยนรหัส ใครก็ตามที่อ่านคู่มือก็เดินเข้าห้องไปได้เลย
ทำไมเรื่องนี้ถึงสำคัญ

ถ้าคุณติดตั้ง (deploy) แอปฯ แล้วลืมตั้งค่า SECRET_KEY จริงๆ ผู้โจมตีจะสามารถ ปลอมแปลงสายรัดข้อมือแอดมินของตัวเอง โดยใช้รหัสเริ่มต้นที่ใครๆ ก็รู้ แล้วเข้าไปอ่านรายงานทุกฉบับ LINE ID ของผู้ใช้ทุกคน และตำแหน่ง GPS ทุกจุดที่คุณเก็บรวบรวมมาได้ นี่ถือเป็นการละเมิดความเป็นส่วนตัวของข้อมูลชุมชนอย่างร้ายแรง

วิธีแก้ไข

อย่าอนุญาตให้มีค่าสำรอง ให้แอปฯ ค้าง (crash) ไปเลยตอนเริ่มทำงานถ้าไม่พบรหัสลับ — คุณทำแบบนี้อยู่แล้วกับ CHANNEL_SECRET ในไฟล์ config.py แค่ก๊อปปี้รูปแบบนั้นมาใช้ครับ:

SECRET_KEY = os.getenv("SECRET_KEY")
if not SECRET_KEY:
    raise ValueError("ไม่ได้ตั้งค่า SECRET_KEY — ระบบปฏิเสธการเริ่มทำงาน")

การให้แอปฯ ค้างตอนเริ่มงานเป็นเรื่อง ดี ในกรณีนี้ เพราะมันจะส่งเสียงเตือนทันที และบังคับให้คนที่ติดตั้งต้องตั้งรหัสลับก่อน ดีกว่าปล่อยให้ระบบรันไปแบบไม่ปลอดภัยเงียบๆ

ความยาก: น้อยมาก — แค่ 3 บรรทัด

Critical

C2 · เมื่อแอปฯ ค้าง ระบบจะส่ง "รูปถ่ายสถานที่เกิดเหตุ" ทั้งหมดไปให้ผู้เยี่ยมชมดู app/main.py:79–86

โค้ดส่วนนี้จะทำงานเมื่อเกิดข้อผิดพลาดที่ไม่ได้คาดคิดขึ้นที่ไหนก็ตามในแอปฯ:

async def global_exception_handler(request, exc):
    error_msg = f"Unhandled Exception: {str(exc)}\n{traceback.format_exc()}"
    print(error_msg)
    return JSONResponse(
        status_code=500,
        content={"detail": "Internal Server Error", "traceback": error_msg}
    )

คำว่า traceback หมายถึงรายงานข้อผิดพลาดภายในแบบละเอียด — ทั้งชื่อไฟล์, เลขบรรทัด, ชื่อฟังก์ชัน และบางครั้งรวมถึงข้อมูลหรือความลับบางอย่าง โค้ดนี้ส่งรายงานทั้งหมดนั้น กลับไปยังใครก็ตามที่ส่งคำขอมา

การเปรียบเทียบ: ลูกค้าสั่งของแล้วระบบผิดพลาด แทนที่จะบอกว่า "ขออภัย มีบางอย่างผิดปกติ" ร้านค้ากลับยื่นแฟ้มที่มีทั้งแผนผังร้าน, ตำแหน่งตู้เซฟ และบันทึกของพนักงานให้ลูกค้าไป มันอาจจะมีประโยชน์กับ คุณ ในการแก้บั๊ก แต่มันอันตรายมากถ้าตกอยู่ในมือคนแปลกหน้า
ทำไมเรื่องนี้ถึงสำคัญ

ผู้โจมตีจะใช้รายละเอียดภายในเหล่านี้เพื่อทำความเข้าใจระบบของคุณและหาช่องโหว่อื่นๆ ต่อไป ข้อมูลนี้รั่วไหลออกมาแม้ว่า ENV=production (โหมดใช้งานจริง) ซึ่งมันย้อนแย้งมาก เพราะคุณพยายามซ่อนหน้า /docs ในโหมดใช้งานจริงอย่างดี แต่กลับมาปล่อยข้อมูลที่สำคัญกว่ามากตรงนี้ แถมมันยังส่งผลเสียร่วมกับข้อ I4 ด้านล่าง (รูปที่หมดอายุทำให้ Dashboard ค้างและส่ง traceback ไปที่เบราว์เซอร์)

วิธีแก้ไข

เก็บรายละเอียดไว้ดู คนเดียว (ใน print / log ของเซิร์ฟเวอร์) แต่ส่งข้อความธรรมดาๆ ที่ไม่บอกอะไรมากให้ผู้เยี่ยมชมพอครับ:

async def global_exception_handler(request, exc):
    print(f"Unhandled Exception: {exc}\n{traceback.format_exc()}")  # เก็บไว้ดูเองใน log
    return JSONResponse(
        status_code=500,
        content={"detail": "Internal Server Error"}  # ไม่มีการรั่วไหล
    )

4. 🟡 ระดับสำคัญ — ควรแก้ในเร็วๆ นี้

Important

I1 · ผู้ใช้ที่ล็อกอินทุกคนสามารถอ่านข้อมูล Dashboard ได้หมด — "Admin" ไม่เคยถูกตรวจสอบจริงๆ app/routes/dashboard.py (ทั้ง 5 endpoints) · app/utils/auth.py:33

คุณเขียนตัวตรวจความปลอดภัยไว้สองตัวใน auth.py:

  • get_current_user — "คนนี้ล็อกอินหรือยัง?"
  • get_current_admin — "คนนี้ล็อกอินแล้ว และ เป็นแอดมินด้วยหรือเปล่า?"

แต่ทุกหน้าของ Dashboard กลับใช้แค่ตัว แรก:

current_user: dict = Depends(get_current_user)   # ใน /stats, /reports, /image, ...

สรุปคือ get_current_admin มีตัวตนอยู่แต่ ไม่เคยถูกเรียกใช้เลย ใครก็ตามที่มีสายรัดข้อมือที่ถูกต้อง — แม้จะไม่ใช่แอดมิน — ก็สามารถอ่านรายงานและดูรูปภาพทั้งหมดได้

การเปรียบเทียบ: คุณจ้างการ์ดมาเฝ้าเพื่อตรวจบัตรแอดมิน แต่คุณดันให้เขาไปยืนเฝ้าอยู่ในห้องเก็บของหลังร้าน แล้วไม่มีใครยืนเฝ้าที่ประตูหน้าจริงๆ เลย ใครที่มีตั๋วอะไรก็ได้ก็เดินเข้างานได้หมด
วิธีแก้ไข

ถ้าหน้าเหล่านี้ตั้งใจให้แอดมินดูเท่านั้น (ซึ่งก็น่าจะเป็นแบบนั้นเพราะมันโชว์ข้อมูลของทุกคน) ให้สลับไปใช้ตัวตรวจแอดมินในทุก endpoint ครับ:

current_user: dict = Depends(get_current_admin)

ถ้าคุณตั้งใจให้ใครที่ล็อกอินก็ได้ดูข้อมูลเหล่านี้จริงๆ ก็ไม่เป็นไรครับ — แต่ควรเขียนคอมเมนต์กำกับไว้หน่อย ไม่งั้นคนที่มาอ่านโค้ดต่อจะนึกว่าเป็นบั๊ก

ความยาก: น้อย — แก้โค้ด 5 บรรทัด

Important

I2 · แอปฯ จะค้างหากไฟล์แบบสำรวจมีการเปลี่ยนแปลงขณะที่มีคนกำลังทำอยู่ app/services/survey_service.py:39, 68–70

ความคืบหน้าของผู้ใช้ (ทำแบบสำรวจไหนถึงขั้นตอนไหน) ถูกบันทึกไว้ในฐานข้อมูล แต่ คำถาม ในแบบสำรวจจะถูกโหลดใหม่จากไฟล์ JSON ทุกครั้งที่เซิร์ฟเวอร์เริ่มทำงาน สองส่วนนี้อาจจะไม่ตรงกันได้

survey = survey_manager.get_survey(survey_version)   # อาจจะส่งค่า None กลับมา!
...
current_route = survey.routes[active_session.current_route_id]        # 💥 ค้างถ้า survey เป็น None
current_question_id = current_route.questions[active_session.current_step]  # 💥 ค้างถ้า step เกินจำนวนคำถาม

สองกรณีที่จะทำให้ระบบพัง:

  • แบบสำรวจถูกเปลี่ยนชื่อหรือลบ: มีคนกำลังทำ "flood_v1" อยู่ แล้วคุณไปเปลี่ยนชื่อไฟล์ พอเขากดตอบ → get_survey จะส่งค่า None กลับมา → None.routes จะทำให้ระบบค้าง
  • แบบสำรวจถูกทำให้สั้นลง: เดิมมี 8 คำถาม คุณแก้เหลือ 5 คำถาม แต่มีผู้ใช้ที่ค้างอยู่ที่ข้อ 6 พอกดตอบ → questions[6] จะหาไม่เจอ → ระบบค้าง
การเปรียบเทียบ: นักศึกษากำลังทำข้อสอบหน้า 8 อยู่ แล้วคุณเดินไปสลับชุดข้อสอบเป็นเวอร์ชันที่สั้นกว่าให้เขา พอเขาพลิกไปหน้า 8 — มันไม่มีหน้านั้นแล้ว เขาจะตกใจและทำอะไรไม่ถูก โค้ดก็ตกใจเหมือนกัน (เกิด error 500) และจะส่ง traceback ออกไปประจานตัวเองเพราะข้อ C2

ถ้าฟิลด์ next ในเส้นทางมีรูปแบบที่ไม่ได้คาดคิด _resolve_next_route จะคืนค่า None ออกไปเงียบๆ ซึ่งทำให้แบบสำรวจจบลงเหมือนว่าทำเสร็จปกติ ความเสี่ยงต่ำเพราะ Pydantic ช่วยตรวจสอบ JSON ตอนโหลดอยู่แล้ว — แต่ถ้าใส่ print เตือนไว้ตรงนี้ จะช่วยให้คุณหาจุดที่แบบสำรวจพังได้เร็วขึ้นครับ

N6 · ข้อมูลการเลือกแบบหลายข้อ (Multi-select) ที่ยังทำไม่เสร็จ ไม่ถูกล้างเมื่อกด "ย้อนกลับ" app/services/survey_service.py (ส่วน go-back)

ถ้าผู้ใช้กำลังเลือกติ๊กถูกหลายๆ ข้ออยู่ครึ่งๆ กลางๆ แล้วดันกด "ย้อนกลับ" ข้อมูลใน pending_multi_select จะไม่ถูกล้างทิ้ง เป็นเคสเล็กๆ ด้านประสบการณ์ผู้ใช้ (UX) ที่เขาอาจจะกลับมาเห็นรอยติ๊กเก่าค้างอยู่ ลองทดสอบดูหน่อยครับว่าเป็นพฤติกรรมที่คุณต้องการหรือเปล่า

6. 🧹 โค้ดที่ไม่ได้ใช้และของเหลือค้าง

สิ่งเหล่านี้ไม่ใช่บั๊ก แต่มันทำให้คนเข้าใจผิดได้ เพราะมันดูเหมือนฟีเจอร์ที่ยังทำไม่เสร็จ การล้างออกจะทำให้โค้ดดูซื่อตรงกับสิ่งที่มันทำจริงๆ ครับ

คืออะไรอยู่ที่ไหนทำไมถึงไม่ได้ใช้
คอลัมน์ image_path models/__init__.py:44, 60 ตารางรายงานทั้งสองยังมีคอลัมน์ image_path อยู่ แต่ตอนนี้รูปภาพถูกดึงมาจาก payload ในรูปแบบ JSON แทนแล้ว (ผ่าน extract_images) ไม่มีส่วนไหนเขียนลงคอลัมน์นี้เลย มันเป็นของเหลือจากการแก้โค้ดครั้งก่อน — ลบออกเถอะครับไม่งั้นคนมาอ่านต่อจะงง
ตาราง IncompleteReport models/__init__.py:48 มีการนิยามและนับจำนวนไว้ แต่ไม่เคยมีการสร้างข้อมูลลงไป (ดูข้อ I7) ให้เลือกเอาว่าจะเชื่อมระบบให้เสร็จหรือจะซ่อนตัวนับไว้ก่อน
get_current_admin utils/auth.py:33 เขียนไว้แต่ไม่ได้ถูกเรียกใช้ (ดูข้อ I1) เมื่อคุณตัดสินใจเรื่องการกั้นแอดมินแล้ว ตัวนี้จะกลับมามีประโยชน์ ตอนนี้มันยังถูกปล่อยทิ้งไว้
การเชื่อมโฟลเดอร์ /uploads main.py:104 ใช้เพื่อให้บริการไฟล์ที่อัปโหลดขึ้นมา แต่ตอนนี้รูปภาพไม่ได้ถูกเซฟลงเครื่องแล้ว (ดึงผ่าน proxy สดๆ) น่าจะเป็นของเก่าที่ค้างมา — ลองเช็คดูว่ามีอย่างอื่นต้องใช้อีกไหม ถ้าไม่มีก็ลบได้ครับ

7. ✅ ส่วนที่ทำได้ดีมาก

การตรวจทานไม่ใช่แค่การหาจุดผิด สิ่งเหล่านี้คือสิ่งที่คุณทำได้ ดี และควรทำต่อไปครับ 🎉

  • ระบบคำนวณเส้นทางที่เป็น "Pure function" (ในไฟล์ routing.py) ฟังก์ชันอย่าง compute_next_state และ compute_go_back_state แค่รับค่าเข้ามาแล้วตัดสินใจส่งผลลัพธ์ออกไป โดยไม่ไปยุ่งกับฐานข้อมูลหรือ LINE API เลย นี่เป็นการออกแบบระดับมืออาชีพมากครับ เพราะมันทำให้ตรรกะที่ซับซ้อนที่สุดในแอปฯ ทดสอบได้ง่ายและเข้าใจได้ชัดเจน น่าประทับใจมากสำหรับโปรเจกต์ปี 1 ครับ
  • การแยกชั้นของโค้ดที่ชัดเจน survey_service (ผู้คุมงาน) → routing (คนตัดสินใจ) → survey_repository (คนจดข้อมูล) → survey_messages (คนจัดหน้าข้อความ LINE) แต่ละไฟล์มีหน้าที่เดียว นี่คือโครงสร้างแบบเดียวกับที่ระบบใหญ่ๆ เขาใช้กันเลยครับ
  • คุณมีการทดสอบ (Tests) จริงๆ มีไฟล์เทสถึง 8 ไฟล์ ครอบคลุมทั้งการหาเส้นทาง, การย้อนกลับ, การเลือกหลายข้อ, จุดพิกัด และการสร้างข้อความ โปรเจกต์นักศึกษาหลายที่ไม่มีแม้แต่ไฟล์เดียว (จุดที่ยังขาด: การทดสอบเรื่องความปลอดภัย/การเข้าสู่ระบบ ซึ่งเป็นก้าวต่อไปที่น่าลองทำเพิ่มครับ)
  • ความใส่ใจในรายละเอียด UX เช่น การล้างคำตอบที่กำลังจะย้อนกลับไปหา (survey_service.py:53–55) และการจำกัดความยาว alt-text ของ LINE ไว้ที่ 400 ตัวอักษร (survey_messages.py:83)
  • Docstrings ที่มีประโยชน์ มีการระบุความตั้งใจไว้ชัดเจน รวมถึงการระบุเงื่อนไข "ไม่ยุ่งกับ DB, ไม่ยุ่งกับ LINE API" — ตัวคุณในอนาคตจะขอบคุณตัวคุณในวันนี้ที่เขียนมันไว้ครับ

8. 🗺️ ลำดับการแก้ไขที่แนะนำ

อย่าพยายามแก้ทุกอย่างพร้อมกันครับ นี่คือลำดับที่สมเหตุสมผล — เริ่มจากความปลอดภัยที่คุ้มค่าที่สุดก่อน แล้วตามด้วยความแข็งแรง และปิดท้ายด้วยความสวยงาม

วันนี้ (15 นาที, ได้ผลมหาศาล): ข้อ C1 (บังคับต้องมี SECRET_KEY) และข้อ C2 (เลิกส่งรายละเอียด error ให้คนนอกดู) ทั้งคู่เป็นการแก้โค้ดเพียงนิดเดียวที่ช่วยปิดช่องโหว่ที่น่ากลัวที่สุดสองจุดได้ทันที

ภายในสัปดาห์นี้: ข้อ I1 (ตรวจแอดมินที่หน้า Dashboard), ข้อ I4 (จัดการรูปที่หมดอายุ), ข้อ I5 (ปฏิเสธวันที่รูปแบบผิด) ทั้งหมดเป็นงานเล็กๆ ที่ช่วยอุดช่องว่างที่เกิดขึ้นจริงได้ดี

9. 📖 อภิธานศัพท์

JWT (JSON Web Token)
"สายรัดข้อมือดิจิทัล" ที่เซิร์ฟเวอร์ออกให้ผู้ใช้หลังล็อกอิน ผู้ใช้จะยื่นมันให้ดูทุกครั้งที่ส่งคำขอเพื่อพิสูจน์ตัวตน ถ้ารหัสลับที่ใช้เซ็นชื่อรั่วไหล ใครๆ ก็ปลอมมันขึ้นมาเองได้ (ดูข้อ C1)
Traceback
รายงานภายในแบบละเอียดที่ Python จะพิมพ์ออกมาเมื่อโค้ดค้าง — มีทั้งชื่อไฟล์, เลขบรรทัด และลำดับการเรียกฟังก์ชัน มีประโยชน์กับนักพัฒนา แต่อันตรายถ้าให้คนแปลกหน้าเห็น (ดูข้อ C2)
Endpoint
URL แต่ละจุดที่เซิร์ฟเวอร์ของคุณคอยตอบคำถาม เช่น GET /api/dashboard/stats แต่ละจุดเปรียบเสมือน "ประตู" เข้าสู่แอปฯ ของคุณ
Dependency (ใน FastAPI)
ฟังก์ชันที่ FastAPI จะรัน ก่อน ที่จะเข้าถึง endpoint นั้นๆ มักใช้เพื่อตรวจสิทธิ์ Depends(get_current_user) หมายถึง "เช็คก่อนว่าเขาล็อกอินหรือยัง" (ดูข้อ I1)
CORS
"Cross-Origin Resource Sharing" — กฎของเบราว์เซอร์ที่กำหนดว่าเว็บไซต์ไหนบ้างที่ได้รับอนุญาตให้เรียกใช้ API ของคุณ รายการอนุญาต (Allow-list) จะระบุชื่อเว็บฝั่งหน้าบ้านที่เชื่อถือได้ (ดูข้อ N3)
Connection pool
ชุดของการเชื่อมต่อฐานข้อมูลที่เปิดค้างไว้เพื่อนำกลับมาใช้ใหม่ เพราะการเปิดท่อใหม่แต่ละครั้งมันช้า แอปฯ เลยเตรียมไว้ล่วงหน้า pool_size คือจำนวนท่อที่มี (ดูข้อ I8)
SSL / การตรวจสอบใบรับรอง (Certificate verification)
SSL ช่วยเข้ารหัสข้อมูลไม่ให้คนแอบฟังได้ ส่วนการตรวจสอบ ใบรับรอง ช่วยยืนยันว่าอีกฝ่ายคือตัวจริง การปิดการตรวจสอบทำให้ข้อมูลยังถูกเข้ารหัสอยู่แต่คุณจะไม่รู้เลยว่ากำลังคุยกับตัวปลอมหรือเปล่า (ดูข้อ I6)
Man-in-the-middle (MITM)
การโจมตีที่คนร้ายมาแอบนั่งอยู่ตรงกลางระหว่างคนสองคน แล้วทำตัวเป็นตัวแทนส่งสารให้ทั้งคู่โดยที่ทั้งคู่ไม่รู้ตัว การตรวจสอบใบรับรองคือเกราะป้องกันหลักเรื่องนี้ (ดูข้อ I6)
Rate limiting
การจำกัดความถี่ที่คนคนหนึ่งจะสามารถเรียกใช้ API ได้ เพื่อป้องกันการส่งสแปมหรือการเดารหัสรัวๆ (ดูข้อ I3)
Pure function
ฟังก์ชันที่ผลลัพธ์ขึ้นอยู่กับค่าที่ส่งเข้าไปเท่านั้น และไม่มีผลข้างเคียงอื่นๆ (ไม่ยุ่งกับฐานข้อมูล ไม่ยุ่งกับเน็ต) ทำให้ทดสอบง่ายและเชื่อถือได้ routing.py ของคุณเต็มไปด้วยสิ่งนี้ ซึ่งเป็นเรื่องดีมากครับ (ดูหัวข้อที่ 7)
nit (nitpick)
ข้อเสนอแนะเรื่องสไตล์เล็กๆ น้อยๆ ที่ไม่เร่งด่วน สามารถข้ามไปก่อนได้ถ้ามีงานด่วนกว่า (คือรายการสี 🟢 ทั้งหมด)
