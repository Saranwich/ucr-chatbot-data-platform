1. The 30-second summary

The survey engine is well-built. The way questions, routes, and branching logic are separated into small "pure" functions (functions that just calculate an answer and don't touch the database or the internet) is genuinely good design — it's easy to test and easy to understand. You even have a real test suite covering it. Nice work.

The weak spots are all around the edges — specifically the security door to your admin dashboard, and what happens when something goes wrong (error handling). These are exactly the areas beginners usually haven't been taught yet, so don't feel bad — they're very fixable.

3. 🔴 Critical — fix before real users

Critical

C1 · A secret password is hard-coded into the source code app/utils/auth.py:9

Your dashboard uses something called a JWT (a digital "wristband" the server hands out to prove someone is logged in). To make a wristband that can't be forged, the server signs it with a secret key. Here is how that key is loaded:

SECRET_KEY = os.getenv("SECRET_KEY", "your-super-secret-key-change-me")

The second value, "your-super-secret-key-change-me", is a fallback: "if nobody set a real secret, use this one." The problem is that this exact string is now public — it's in your code on GitHub and written in your CLAUDE.md.

Analogy: It's like a school that buys a fancy lock for the server room, but ships every lock pre-set to the combination 0-0-0 and prints that combination in the manual. If a teacher forgets to change it, anyone who read the manual walks straight in.
Why it matters

If you deploy the app and forget to set a real SECRET_KEY, an attacker can forge their own admin wristband using the known default, and then read every report, every user's LINE ID, and every GPS location you collected. That's a privacy breach of your community's data.

The fix

Don't allow a fallback. Crash on startup if the secret is missing — you already do exactly this for CHANNEL_SECRET in config.py, so just copy that pattern:

SECRET_KEY = os.getenv("SECRET_KEY")
if not SECRET_KEY:
    raise ValueError("SECRET_KEY is not set — refusing to start.")

A crash on startup is good here: it's loud, it happens immediately, and it forces whoever deploys to set the secret. Far better than silently running insecure.

Effort: tiny — 3 lines

Critical

C2 · When the app crashes, it emails the full crime-scene photos to the visitor app/main.py:79–86

This block runs whenever any unexpected error happens anywhere in the app:

async def global_exception_handler(request, exc):
    error_msg = f"Unhandled Exception: {str(exc)}\n{traceback.format_exc()}"
    print(error_msg)
    return JSONResponse(
        status_code=500,
        content={"detail": "Internal Server Error", "traceback": error_msg}
    )

The word traceback means the full internal error report — file names, line numbers, function names, and sometimes pieces of data or secrets. This code sends that whole report back to whoever made the request.

Analogy: A customer's order fails, so instead of saying "sorry, something went wrong," the shop hands them a folder containing the store's floor plan, the safe's location, and the staff's notes. Helpful for you to debug — dangerous to hand to a stranger.
Why it matters

Attackers use these internal details to map out your system and find more holes. It also leaks even when ENV=production — which is ironic, because you carefully hide the /docs page in production but then expose far more here. It also combines badly with finding I4 below (an expired photo crashes the dashboard and dumps a traceback to the browser).

The fix

Keep the detail for yourself (the print / server logs), but give the visitor a plain, boring message:

async def global_exception_handler(request, exc):
    print(f"Unhandled Exception: {exc}\n{traceback.format_exc()}")  # logged for you
    return JSONResponse(
        status_code=500,
        content={"detail": "Internal Server Error"}  # nothing leaked
    )

Effort: tiny — delete one field

4. 🟡 Important — should fix soon

Important

I1 · Any logged-in user can read the whole dashboard — "admin" is never actually required app/routes/dashboard.py (all 5 endpoints) · app/utils/auth.py:33

You wrote two security guards in auth.py:

  • get_current_user — "is this person logged in at all?"
  • get_current_admin — "is this person logged in AND an admin?"

But every dashboard endpoint uses the first one:

current_user: dict = Depends(get_current_user)   # on /stats, /reports, /image, ...

So get_current_admin exists but is never used anywhere. Any valid wristband — even a non-admin one — can read all reports and images.

Analogy: You hired a bouncer who checks for admin badges, but you stationed him in a back room and put nobody on the actual door. Everyone with any ticket walks in.
The fix

If these pages are meant for admins only (they look like it — they show everyone's data), swap the dependency on each endpoint:

current_user: dict = Depends(get_current_admin)

If you genuinely want any logged-in user to see them, that's fine — but leave a comment saying so, otherwise the next reader assumes it's a bug.

Effort: small — change 5 lines

Important

I2 · The app crashes if a survey file changes while someone is mid-survey app/services/survey_service.py:39, 68–70

A user's progress (which survey, which step) is saved in the database. The survey questions are loaded fresh from JSON files every time the server starts. These two things can drift apart.

survey = survey_manager.get_survey(survey_version)   # can return None!
...
current_route = survey.routes[active_session.current_route_id]        # 💥 if survey is None
current_question_id = current_route.questions[active_session.current_step]  # 💥 if step out of range

Two ways this blows up:

  • Survey renamed/deleted: someone started "flood_v1", you rename it, they tap an answer → get_survey returns None → None.routes crashes.
  • Survey shortened: a survey had 8 questions, you trim it to 5, a user sitting on step 6 answers → questions[6] is out of range → crash.
Analogy: A student is on page 8 of an exam. You swap their booklet for a shorter version. They turn to page 8 — it doesn't exist, and they panic. The code panics the same way (a 500 error), which then leaks a traceback because of C2.
The fix

Check for these cases and gently restart the user instead of crashing:

survey = survey_manager.get_survey(survey_version)
if survey is None or active_session.current_route_id not in survey.routes:
    await repo.clear_session(db, user_id)
    await messages.send_text(reply_token, "แบบสำรวจมีการอัปเดต กรุณาเริ่มใหม่อีกครั้งครับ", line_bot_api)
    return

Effort: medium — add guards in 2 spots

Important

I3 · The health-check rate limiter slowly leaks memory (and doesn't work on AWS) app/main.py:89, 91–101

To stop people spamming /api/health, you remember the last visit time of every IP address:

health_check_limits = defaultdict(float)   # {ip_address: last_seen_time}

Two problems:

  1. It never forgets. Every new IP that ever visits adds an entry that's never removed. Over months this dictionary grows without limit — a slow memory leak. Worse, an attacker who sends requests from thousands of fake IPs can balloon it on purpose.
  2. It doesn't work on AWS Lambda. Your main.py:130 wraps the app in Mangum, meaning it runs on Lambda. Lambda throws away memory between requests, so this dictionary resets constantly and the limit barely applies.
Analogy: A doorman writes every visitor's name on an infinitely long scroll to remember them — but on Lambda he gets amnesia after each visitor, so the scroll is both useless and endlessly growing.
The fix

For a simple health check, the easiest correct option is to remove the custom limiter entirely — health checks rarely need protecting. If you do need rate-limiting elsewhere, use a library like slowapi backed by a shared store (Redis), which works across Lambda invocations.

Effort: small — delete it, or swap to a library

Important

I4 · Viewing an expired photo throws a 500 instead of a clean "not found" app/routes/dashboard.py:121–131

Survey photos aren't saved to your own storage — they live on LINE's servers and are fetched live each time the dashboard asks for them. LINE deletes these after a while. When that happens, this code has no safety net:

blob_api = AsyncMessagingApiBlob(api_client)
content = await blob_api.get_message_content(image_id)  # throws if expired/invalid
return Response(content=content, media_type="image/jpeg")

If the photo is gone, that line throws → the request 500s → and (thanks to C2) the dashboard gets a traceback in its face instead of a tidy "image unavailable."

The fix

Wrap it and return a clean 404:

try:
    content = await blob_api.get_message_content(image_id)
except Exception:
    raise HTTPException(status_code=404, detail="Image not found or expired")
return Response(content=content, media_type="image/jpeg")

(Bonus: media_type is hard-coded to image/jpeg, so a PNG would be mislabeled. Minor, but worth noting alongside this.)

Effort: small — wrap in try/except

Important

I5 · A typo in the date filter silently returns every report app/routes/dashboard.py:81–86

The reports endpoint lets you filter by date, e.g. ?date=2026-06-08. If the date is malformed, this happens:

try:
    target_date = datetime.strptime(date, "%Y-%m-%d").date()
    query = query.where(...)
except ValueError:
    pass  # Invalid date format, skip filtering

The word pass means "do nothing." So if someone types a bad date, the filter is silently skipped and they get the entire database of reports back — the opposite of what they asked for.

Analogy: You ask a librarian for "books from June." They mishear, shrug, and wheel out every book in the library. No warning that they didn't understand you.
The fix

Tell the caller they made a mistake instead of guessing:

except ValueError:
    raise HTTPException(status_code=400, detail="Invalid date format, expected YYYY-MM-DD")

Effort: tiny — one line

Important

I6 · Database encryption checks are switched off app/database/__init__.py:29–31

When connecting to a hosted database, this code sets up the encrypted link but then disables the safety checks:

ctx = ssl.create_default_context()
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE

CERT_NONE means "don't bother verifying who you're actually talking to." The traffic is still scrambled, but you can no longer be sure the thing on the other end is really your database.

Analogy: You speak in code so eavesdroppers can't understand you — but you never check the person you're whispering to is your friend, not an impostor wearing their jacket. (This is called a "man-in-the-middle" risk.)
Why it's only 🟡, not 🔴

This is a very common workaround for managed databases (Render, Heroku) whose certificates are awkward, and it's triggered only when your database URL contains sslmode. It's a known, deliberate trade-off — but right now it turns on automatically rather than being an explicit, conscious choice.

The fix

Best: download your database provider's CA certificate and verify against it (CERT_REQUIRED + cafile=...). Minimum: gate this behind an explicit env flag like DB_INSECURE_SSL=true so it can't silently happen in production.

Effort: medium — depends on provider

Important

I7 · The "incomplete reports" counter will always show 0 — nothing ever creates one app/models/__init__.py:48 · app/services/survey_repository.py:60

You have a whole database table, IncompleteReport, designed to record people who abandon a survey partway (with a drop_off_step field — clever, it tells you which question scares people off). The dashboard even counts them:

incomplete_count = await db.scalar(select(func.count(IncompleteReport.report_id)))

But I searched the whole codebase: nothing ever creates an IncompleteReport. When a survey finishes you make a CompletedReport; when one is abandoned, the session just sits there or gets overwritten next time. So that "incomplete reports" number on your dashboard is permanently 0 and quietly misleading.

Analogy: You installed a "students who dropped the class" counter on the wall, but never wired it to anything. It proudly reads 0 forever, so everyone assumes nobody ever drops.
The fix

This needs a background job (a timer) that periodically finds SurveySession rows that haven't been touched in, say, 30 minutes, converts them to IncompleteReport (copying current_route_id/current_step into the drop-off fields), and deletes the session. Until that exists, consider hiding the incomplete counter so it doesn't mislead. Worth filing as its own issue.

Effort: larger — needs a scheduled task

Important

I8 · The database is configured for a single connection — concurrent users will queue app/database/__init__.py:41–43 

engine = create_async_engine(
    ...,
    pool_size=1,
    max_overflow=0,     # at most ONE database connection at a time
)

A "connection pool" is a set of open phone lines to the database. pool_size=1, max_overflow=0 means there is exactly one line. If two people answer survey questions at the same instant, the second one waits for the first to hang up.

Analogy: A busy clinic with one phone line. Patients don't get turned away, but they wait — and if the call ahead hangs, everyone behind is stuck.
Why it might be intentional

On AWS Lambda, each running copy handles one request anyway, and databases limit total connections — so people sometimes set this to 1 on purpose. If that's your reasoning, leave a one-line comment. If you ever run this as a normal always-on server (not Lambda), raise it to something like pool_size=5 so several users can be served at once.

Effort: tiny — change a number, or add a comment

Everywhere you report status you use print(). Fine for a class project, but Python's built-in logging module lets you turn detail up or down, add timestamps, and (importantly) keep error details out of HTTP responses. Worth switching once the app is real.

If a route's next field is an unexpected shape, _resolve_next_route quietly returns None, which ends the survey as if it finished normally. Low risk because Pydantic validates the JSON at load time — but a print warning here would help you spot a broken survey faster.

7. ✅ What's genuinely good

Reviews aren't only about problems. These are things you did well — keep doing them. 🎉

  • The "pure function" routing engine (routing.py). Functions like compute_next_state and compute_go_back_state just take inputs and return a decision — they never touch the database or LINE. This is a professional-level design choice: it makes the trickiest logic in your app easy to test and reason about. Genuinely impressive for a first-year project.
  • Clear separation of layers. survey_service (orchestration) → routing (decisions) → survey_repository (database) → survey_messages (LINE formatting). Each file has one job. This is exactly how bigger systems are structured.
  • You have real tests. Eight test files covering routing, go-back, multi-select, location points, and message building. Many student projects have none. (Gap: nothing tests the auth/security paths yet — a great next thing to add.)
  • Thoughtful UX details, like clearing the answer you're returning to when a user taps "go back" (survey_service.py:53–55), and capping LINE's alt-text at 400 characters (survey_messages.py:83).
  • Helpful docstrings that state intent, including the "no DB, no LINE API" contract — future-you will thank present-you.

9. 📖 Glossary

JWT (JSON Web Token)
A signed digital "wristband" the server gives a user after login. The user shows it on each request to prove who they are. If the signing secret leaks, anyone can forge one. (See C1.)
Traceback
The detailed internal report Python prints when code crashes — file names, line numbers, the chain of function calls. Useful to developers, dangerous to expose to strangers. (See C2.)
Endpoint
A single URL your server answers, e.g. GET /api/dashboard/stats. Each one is a "door" into your app.
Dependency (in FastAPI)
A function FastAPI runs before your endpoint, often to check permissions. Depends(get_current_user) means "first make sure they're logged in." (See I1.)
CORS
"Cross-Origin Resource Sharing" — browser rules about which websites are allowed to call your API. The allow-list says which front-end addresses are trusted. (See N3.)
Connection pool
A set of reusable open connections to the database. Opening one is slow, so apps keep a few ready. pool_size is how many. (See I8.)
SSL / certificate verification
SSL scrambles traffic so eavesdroppers can't read it. Certificate verification additionally confirms the other end is who it claims to be. Turning verification off keeps the scrambling but loses the identity check. (See I6.)
Man-in-the-middle (MITM)
An attack where someone secretly sits between two parties, impersonating each to the other. Certificate verification is the main defense. (See I6.)
Rate limiting
Restricting how often someone can hit an endpoint, to stop spam/abuse. (See I3.)
Pure function
A function whose output depends only on its inputs, with no side effects (no database, no network). Easy to test and trust. Your routing.py is full of these — that's a good thing. (See section 7.)
nit (nitpick)
A tiny, non-urgent style suggestion. Safe to ignore under deadline. (The 🟢 items.)
